# 4. CAPTURE-OR-REUSE

**VERIFIED_BY_CODE + VERIFIED_BY_TEST (T2)** para el caso normal:

```
ORIGINAL(ble=1) → beginApply#1 [capture, IDLE→APPLYING] → BOOSTED(ble=0)
  → beginApply#2 (re-apply/cambio de perfil) → load(): state=APPLYING ∈ active-list
  → REUSE (BoostSessionManager.kt:185-195) → baseline sigue ble=1 ✔
```

T2 lo afirma en JVM; el ciclo 5 del device lo mostró (baseline capturó anim=1.0/touch=null con el dispositivo boosteado NO — capturó limpio). Tras RESTORED el beginApply re-captura, y es correcto: los valores actuales son otra vez los originales (el restore fue verificado) o voluntad del usuario (conflictos) — el baseline nuevo es legítimo.

**PERO — CONTRADICTED parcialmente por la fuga 4.D (race de estado, no de valor):**

```
t0 toggleBoost(OFF) → scope.launch{ restoreVerified() } → save(RESTORING)
t2 toggleBoost(ON)  → beginApply → load(): RESTORING ∈ active → REUSE ✔ → save(APPLYING)
t4 el restore del t0 (aún en vuelo, 44 keys × Shizuku = 2-4s) termina → allOk → save(RESTORED)
   → PISA el APPLYING del t2 (restoreVerified no re-valida el estado antes del save final)
t5 writers del boost t2 aplican settings
t6 PROCESS DEATH → archivo dice RESTORED → arranque → clear() → SIN RECOVERY
   → boost aplicado + proceso muerto + sin baseline → residuos permanentes (defecto F4 original)
```

El VALOR del baseline no se corrompe (4.B es inofensivo: doble restore idempotente); lo que se pierde es el MARCADOR de que había un boost activo. La ventana es real (usuario apagando y encendiendo el boost en <4s — no es un caso raro: el switch es el control principal de la UI). Clasificación de la ruta: **SUPPORTED_BUT_INCOMPLETE** (el happy-path está demostrado; la race no tiene guard) — y es el hallazgo principal de esta post-auditoría.

# 7. ATOMICITY

VERIFIED_BY_CODE, punto por punto (BoostSessionStore):
- temp en mismo directorio (mismo FS → rename atómico POSIX) ✔ :27-28
- `fos.fd.sync()` antes de cerrar y antes de rename ✔ :68
- falla de escritura/fsync → catch → tmp borrado → false → beginApply **cancela el boost** (fail-closed, GameSessionManager:183-190) ✔
- muerte pre-rename → tmp huérfano + archivo anterior íntegro; load() descarta tmp ✔ :37-38
- muerte post-rename → archivo nuevo completo ✔
- JSON corrupto → .corrupt (evidencia) + delete + operar SIN baseline (Caso C: no inventa) ✔ :48-55

**Matiz de rigor (no exigido por F4 pero atribuido de más en el reporte F3B):** no hay `fsync(dirfd)` tras el rename → la atomicidad es **REAL contra process death** (SIGKILL no afecta la página cache del FS) pero **PARCIAL contra power-loss** (el rename puede no llegar a disco). El enemigo de F4 es process death → garantía suficiente; el reporte original no debía atribuir más.

Q9: no hay versión anterior recuperable (solo .corrupt como evidencia, no restaurable) — aceptable para el alcance.

# 15. SUPPORTED BUT INCOMPLETE

1. **Race 4.D (hallazgo principal)**: restore-en-vuelo puede finalizar con `save(RESTORED)` pisando un `APPLYING` recién creado por un toggleBoost(OFF→ON) rápido → muerte posterior sin marcador → residuos permanentes. El guard ausente es un re-check del estado previo al save final (o serializar beginApply/restoreVerified con un mutex del manager). No demostrada en device (requiere timing <4s) pero la ruta es real por construcción de código.
2. **Writer sin gate**: `restoreSavedSettings` escribe pointer_speed (key del contrato) pre/durante recovery → posible falso conflicto B que descarta el baseline de esa key.
3. **Ambigüedad null de readSetting** con Shizuku caído → recovery puede reportar allOk falso (todo skip/conflict) y hacer clear() con residuos presentes. Conservador (no muta) pero pierde el marcador.
4. **Caso A teórico**: usuario que fija manualmente el valor boosted es sobrescrito por el restore (indistinguible por diseño).
5. **Normalización cosmética**: put escribe "1" por "1.0".
6. **appliedValueOf(refresh) incompleto** para el writer de ProfileManager (90.0 de GAMING no catalogado → residuo 90.0 se conservaría por conflicto).
7. **BASELINE_CAPTURED es estado muerto** (nunca se persiste — divergencia diseño/código cosmética).

# 19. RECOMMENDATION

# **REVIEW REQUIRED BEFORE COMMIT**

El trabajo F4 es sólido, el PASS de los escenarios probados es genuino, y NO hay razón para descartar la implementación. Pero la race 4.D es exactamente del tipo que F4 existía para eliminar (residuos permanentes por pérdida de marcador), con una ventana alcanzable por un usuario real (el switch principal, toggling rápido). Recomendación concreta antes del commit:

1. **Cerrar la race 4.D** (fix pequeño): serializar beginApply/restoreVerified con un Mutex del BoostSessionManager, o re-verificar el estado del archivo en el save final del restore (solo pasar a RESTORED si el estado actual sigue siendo RESTORING). ~5 líneas.
2. **Gate en restoreSavedSettings** (pointer_speed) o excluir pointer_speed del catálogo de valores dinámicos tratándolo como APP_ONLY. ~3 líneas.
3. **Desambiguar readSetting** (null de fallo vs ausencia: usar un Result<String?> o marcador) para que Shizuku-caído produzca FAILED/no-avance en vez de falso allOk. ~10 líneas.
4. (Opcional) Eliminar BASELINE_CAPTURED muerto o emitirlo.
5. (Opcional) Añadir appliedValueOf para refresh por perfil (90.0) o dejar documentado el conflicto-conservador.

Con (1)-(3) el veredicto subiría a F4 PASS CONFIRMED; sin ellas, el commit dejaría una race conocida y documentada en un mecanismo cuya única razón de existir es eliminar ese tipo de rachas. La decisión es del owner; esta auditoría no implementa nada.
