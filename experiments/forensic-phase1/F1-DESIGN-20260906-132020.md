## 1. EXECUTIVE SUMMARY

Diseño de corrección para F1. Tres decisiones arquitectónicas centrales:

1. **Reemplazar el contrato fire-and-forget** `executePrivilegedCommand(): Unit` por un **resultado estructurado `ExecResult`** que distinga `EXECUTED` (comando corrió, efecto NO verificado) de `VERIFIED` (postcondition confirmada por read-back), sin duplicar la abstracción `SettingRead` de F4 (se reutiliza).
2. **`set-process-limit` → se ELIMINA del pathway normal**, porque ya existe en el contrato F4 un mecanismo reversible equivalente (`activity_manager_constants max_cached_processes`), y `set-process-limit` es global, sin read-back persistible y redundante. **`drop_caches` → se ELIMINA** (irreversible, global, root-only, sin beneficio demostrable; `RamManager.kt:66/123` ya lo documenta como perjudicial). **`force-idle` → se ELIMINA el uso de ResourceGovernor como "optimización de pantalla apagada"** (pertenece a Doze/gestión de energía, no al boost reversible).
3. **`ResourceGovernor` se vuelve state-aware**: el screen-off/on consulta la máquina F4 y solo actúa en estados consistentes (`ACTIVE`/`IDLE`), **jamás** en `APPLYING`/`RESTORING`/`RECOVERY_REQUIRED`, con mutex compartido con la FSM F4 para eliminar carreras.

El diseño apunta a que **ninguna mutación F1 quede sin verificación o fuera del modelo de sesión**. Las mutaciones que no pueden cumplir el contrato F4 (baseline + read-back + restore verificable) **no se aplican automáticamente**.

## 5. PROPOSED EXECUTION-RESULT CONTRACT

### 5.1 Nombres de estados

Se propone un sealed result, ubicado en un nuevo archivo `manager/exec/PrivilegedResult.kt` (sin tocar F4):

```kotlin
sealed class ExecOutcome {
    data class PROCESS_START_FAILED(reason: String?) : ExecOutcome()      // no arrancó el proceso
    data class EXIT_NONZERO(exit: Int, stderr: String?) : ExecOutcome()   // corrió, exit≠0
    data class STDERR_ERROR(stderr: String) : ExecOutcome()               // exit 0 pero stderr trae error del comando interno
    data class TIMEOUT(timeoutMs: Long) : ExecOutcome()                   // excedió el tiempo
    data class PRIVILEGE_UNAVAILABLE(reason: String?) : ExecOutcome()     // Shizuku/Rish no disponibles y fallback sin privilegios
    data class EXECUTED(out: String) : ExecOutcome()                      // corrió exit 0, efecto NO verificado
}
```

Y un wrapper que une ejecución + verificación:

```kotlin
data class ExecResult(
    val outcome: ExecOutcome,
    val verified: Boolean,        // false ⇒ solo EXECUTED, sin postcondition
    val deviceValue: SettingRead? // si había read-back, el valor releído (reusa SettingRead de F4)
)
```

### 5.2 Distinciones clave

| Caso | Representación | ¿Cuenta como éxito? |
|---|---|---|
| Comando corrió, exit 0, sin verificación | `EXECUTED` + `verified=false` | **NO usable como "aplicado"** |
| Comando corrió, exit 0, stderr con error del comando interno | `STDERR_ERROR` | NO |
| Comando corrió, exit 0, postcondition confirma | `EXECUTED` + `verified=true` + `deviceValue==expected` | SÍ |
| Corrió pero read-back falló | `EXECUTED` + `verified=false` + `deviceValue=ReadFailed` | NO (fail-closed) |
| No corrió (start fail / timeout / privilege) | `PROCESS_START_FAILED`/`TIMEOUT`/`PRIVILEGE_UNAVAILABLE` | NO |

### 5.3 Qué pertenece a F1 vs F3

- **F1**: definir el **contrato** (`ExecOutcome`), el **reader** de read-back, y la **política** (qué mutaciones aceptan `EXECUTED` y requieren `VERIFIED`). ResourceGovernor **consume** `ExecResult`.
- **F3**: sigue siendo **dueño del mecanismo de ejecución** (`ShizukuExecutor`/`RishExecutor` y el fallback). F1 **NO reescribe** a los executors; solo se apoya en `Result<String>` que ya exponen y añade `STDERR_ERROR`/`stdout-inspection` como capa en la política de F1. El fallback Runtime se **marca** (`PRIVILEGE_UNAVAILABLE`) para que F1 no lo confunda con éxito real.

### 5.4 Cómo evitar que ResourceGovernor descarte información

- `executePrivilegedCommand` pasa a **devolver** `List<ExecResult>` (uno por sub-comando del split). Los callers (ResourceGovernor y el resto) que hoy ignoran el retorno lo recogen y loguean el outcome por comando con `addLog` (nivel dependiente: `VERIFIED`=DEBUG, `EXECUTED`=WARN "sin verificar", resto=WARN/ERROR).

## 6. PROCESS-LIMIT DESIGN → DECISIÓN: **ELIMINAR** del pathway F1

**Justificación (evidencia):**
- `set-process-limit 8` es **GLOBAL** (todas las apps, user system), **persiste por vida del proceso de la app y de system_server**, y su restore (`-1`) depende del lifecycle `SCREEN_ON`. Si muere el proceso antes de screen-on, queda `8` (AUDIT F1-01/02).
- **No hay read-back persistible**: no existe `settings get` para process-limit; `ActivityManager.getProcessLimit()` es una API de app privilegiada, no un setting consultable por el shell como `settings get`.
- **Redundant**: F4 ya controla el límite de procesos en caché de forma **reversible y verificable** vía `activity_manager_constants max_cached_processes=128` (BoostSessionManager.kt:37,105; SystemTweaks.kt:84). Este es el mecanismo correcto: es un `settings put global` → cabe en el modelo de baseline/restore/read-back de F4.

**Por tanto:** se propone
- **Eliminar** `cmd activity set-process-limit 8` y `-1` de `handleScreenOff/On`.
- **Dejar** la limitación de procesos a cargo del contrato F4 existente (`max_cached_processes=128` en el boost).
- **No añadir** field nuevo a la sesión F4 para process-limit (evita ampliar el modelo sin necesidad; el mecanismo ya cubierto es suficiente y más seguro).

Si en el futuro se quisiera un límite screen-off adicional, deberá pasar por un mecanismo idéntico (campo de sesión con baseline + restore + read-back verificable), no por la API global.

## 7. DROP_CACHES DECISION → DECISIÓN: **ELIMINAR**

**Milimétrica (no por asunción):**
1. **Beneficio real:** nulo para rendimiento de juego; la pagecache purgada se re-llena al re-leer discos → I/O spike y jank al relanzar (contrario al objetivo). `RamManager.kt:66` (`sin drop_caches`) y `RamManager.kt:123` (`evita lags extremos y kills del LMK`) documentan el mismo juicio ya en el código.
2. **Alcance:** global (toda la máquina), no la app.
3. **Irreversibilidad:** no existe restore; el drop es instantáneo.
4. **Privilegios:** root (uid 0). El shell uid 2000 de Shizuku/Rish es bloqueado por SELinux. En ZTE no-rootado es no-op.
5. **Seguridad:** operación sobre `/proc/sys/vm/...` con claims de "liberar RAM" no verificables.
6. **Verificación:** solo superficial (`/proc/meminfo`); no hay confirmación de que el efecto esperado exista.
7. **Compatibilidad/recuperación:** F4 no puede (y no debe) restaurar una cache-drop.

**Conclusión justificada:** una operación **irreversible, global, root-only, sin verificación y sin beneficio demostrado NO pertenece al camino reversible de un boost**. Se **elimina** de `ResourceGovernor`. El `drop_caches 3` de `RecoveryManager.kt:90` queda **fuera del alcance de F1** (es un recovery de emergencia, no un boost); se recomienda revisarlo en su propia fase, pero no se toca aquí por regla de no-regresión.

## 8. FORCE-IDLE DECISION → DECISIÓN: **ELIMINAR del flujo del boost**

- Qué hace: `dumpsys deviceidle force-idle` fuerza Doze profundo.
- Reversible?: El sistema sale de Doze al interactuar/screen-on, pero el "force-idle" solicita mantenerlo; no hay un `undo` explícito garantizado.
- Baseline/restore: no es un setting; no hay baseline ni restore SDK.
- Pertenencia: es **gestión de energía de batería**, NO un ajuste de rendimiento reversible del modelo de sesión F4.
- **Decisión:** se elimina la llamada a `force-idle` desde `handleScreenOff`. `PowerOptimizer.forceDoze()` (que sigue existiendo como función) queda **disponible solo como acción manual/opcional de batería**, fuera del screen-off automático. No se borra la función (evita tocar PowerOptimizer = no-regresión F2), solo se deja de invocar desde el receiver.

## 9. LIFECYCLE STATE MACHINE (gate F1 × F4)

`ResourceGovernor.handleScreenOff/On` consulta `boostSession.currentState()` ANTES de mutar. Tabla:

| Estado F4 | SCREEN_OFF | SCREEN_ON | Acción permitida |
|---|---|---|---|
| `IDLE` / `RESTORED` | SÍ (anims 0.5 efímero) | SÍ | Mutar solo si no hay boost pendiente; NINGUNA mutación fuera del contrato |
| `ACTIVE` | SÍ (anims 0.5 — pero vía F4 si se quiere persistir) | SÍ | Permitido; anims al valor del perfil |
| `APPLYING` | **BLOQUEADO** | **BLOQUEADO** | No mutar (apply en vuelo) |
| `RESTORING` | **BLOQUEADO** | **BLOQUEADO** | No mutar (restore en vuelo) |
| `RECOVERY_REQUIRED` | **BLOQUEADO** | **BLOQUEADO** | **Jamás** mutar (bloquea reboost que podría interferir con recovery) |
| `BASELINE_CAPTURED` | SÍ (inofensivo) | SÍ | Efímero, sin escritura de contrato |
| `FAILED` (nuevo estado conceptual opcional) | **BLOQUEADO** | **BLOQUEADO** | No aplicar |

**Regla central:** `RECOVERY_REQUIRED + SCREEN_OFF` **nunca** dispara una mutación. `RESTORING + SCREEN_OFF` y `APPLYING + SCREEN_OFF` **nunca** disparan. Solo `ACTIVE`/`IDLE`/`RESTORED` permiten mutaciones efímeras de screen-off/on, y esas mutaciones son **solo las reversibles** (anims vía F4 si se quieren persistir, o efímeras marcadas tras aplicadas).

## 10. CONCURRENCY / RACE MODEL

**Diseño:** una **ried cola/actor por sesión** compartida, no locks dispersos. Reutilizar el principio de **session identity + commit guard** que F4 ya implementó (BoostSessionManager restoreVerified).

- **Owner de la sesión:** `BoostSessionManager` (F4) es el único que transiciona la FSM.
- **ResourceGovernor** NO transiciona la FSM; solo **consulta** `currentState()` y, si le corresponde, invoca escrituras que **delegan** a F4 (anims) o son **efímeras auto-marcadas** (trim-caches).
- **Cola única:** todas las operaciones de mutación (apply, restore, screen-off, screen-on, recovery) se encolan en un único `CoroutineScope`/`Channel` de ejecución serializado (`Mutex` por sesión). Ninguna mutación arranca si otra está en curso.
- **Prioridad:** recovery > restore > apply > screen-events. Un `screen-off` que llega durante `RESTORING` se descarta (gate) en lugar de colarse.
- **Evento antiguo vs sesión nueva:** antes de confirmar/escribir, re-validar session identity (igual que el commit guard F4). Un screen-off disparado con una sesión vieja no pisa el estado de una sesión nueva.
- **Re-apply durante recovery:** bloqueado por el gate (§9). 

Esto **no duplica** el mecanismo F4: reutiliza `currentState()` + session-id como fuente de verdad; el `Mutex` es solo para las escrituras efímeras de ResourceGovernor que F4 no cubre.

## 12. READ-BACK CONTRACT

- **Reutilizar** `sealed SettingRead { Present(value) | Absent | ReadFailed(reason) }` de F4 (BoostSessionManager.kt:152-156). No duplicar.
- `write → read → compare → [VERIFIED | FAILED]` se expone como helper (en F1) que usa `readSetting`-como paradigma (Settings API o shell `settings get`).
- **`exit 0` NO es prueba de éxito.** Todo outcome sin read-back queda `EXECUTED` con `verified=false`.
- El reader acepta un path distinto por mutación: `settings get` para anims/keys; para `activity_manager_constants` → `settings get global activity_manager_constants`; para mutaciones no-settings (como trim-caches) → no hay read-back → stay `EXECUTED`.

## 13. FAIL-CLOSED RULES

| Condición | Comportamiento |
|---|---|
| No hay Shizuku ni Rish | `PRIVILEGE_UNAVAILABLE` → mutación **NO aplicada**; en el boost ya es fail-closed (F4 capture aborta si read falla). Para screen-off: no muta. |
| Shizuku responde error | `EXIT_NONZERO`/`STDERR_ERROR` → no muta; se loguea. |
| Runtime fallback ejecuta sin privilegios | **Marcar como `PRIVILEGE_UNAVAILABLE`** (no considerar "aplicado"). No usar fallback para mutaciones de contrato. |
| write devuelve error | No aplica baseline/inventory update; `RECOVERY_REQUIRED` si es parte de sesión activa. |
| read-back falla | Fail-closed: `verified=false`, `deviceValue=ReadFailed` → tratar como fallo (no éxito). |
| baseline no puede capturarse | `beginApply` de F4 ya aborta (capture incompleto → false). |
| restore no puede verificarse | F4 ya persiste `RECOVERY_REQUIRED`. |
| muerte durante APPLY | F4: estado `APPLYING` persistido → recovery al arranque. |
| muerte durante RESTORE | F4: estado `RESTORING` persistido → recovery al arranque. |

**Regla dominante:** *no saber si mutó* ⇒ *asumir que no mutó* (para limitar aplicaciones), y *no saber si restauró* ⇒ *asumir no restaurado* (mantener recovery).
